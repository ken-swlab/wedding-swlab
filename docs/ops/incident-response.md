# インシデント対応の手順（Issue #104）

最終更新: 2026-10-12

事故が起きたとき・起きたかもしれないときに、1 人で、慌てずに動くための手順。**先に止める、消さない、書き残す。**

- このリポジトリは公開されている。**連絡先・個人名・事故の詳細を、このファイルにも Issue にも書かない。**連絡先はパスワードマネージャーの「緊急連絡先」に置き、事故の記録は、公開されない場所（非公開のメモ）に書く。
- 法律上の判断（報告の義務があるか、誰に・いつまでに）は、ここに書いた目安で決めず、**専門家（弁護士）と所管の窓口に確かめる。**
- 関連: [alerting.md](alerting.md)（気づく）、[backup-restore.md](backup-restore.md)（戻す）、[../security/rotation-runbook.md](../security/rotation-runbook.md)（鍵を入れ替える）、[../security/csp-check.md](../security/csp-check.md)（CSP を戻す）。

## 1. 重大度

迷ったら、重いほうで扱う。

| 重大度 | 例 | 動き出すまで | 連絡 |
|---|---|---|---|
| **S1 重大** | 個人情報（本名・アレルギー・顔写真・位置情報）が外に出た、またはその疑い。サービスアカウントの鍵や運用アカウントが破られた。データが消えた・書き換えられた | すぐ（気づいた時点で封じ込め） | 新郎新婦（依頼主）、必要ならゲスト・提供先の会社。報告の義務を専門家に確認 |
| **S2 高** | 本番が使えない（ログイン・投稿ができない）。当日の投影が止まった。秘密が漏れたが、使われた形跡は無い | 1 時間以内（当日は、すぐ） | 当日なら会場の担当者。それ以外は、長引くときにゲストへ告知 |
| **S3 中** | 一部の機能の不具合（顔検出・音声・高画質版の公開の遅れ）。総当たりの試行がレート制限で止まっている | 当日中 | 不要 |
| **S4 低** | 外部からの脆弱性の報告（悪用の形跡なし）。依存の脆弱性の通知 | 3 営業日以内に受領の返信（[disclosure-policy.md](../security/disclosure-policy.md)） | 報告者 |

## 2. 最初の 15 分

1. **時刻を書く。**気づいた時刻、何を見て気づいたか。以後、やったことを時刻つきで書き続ける（§6 のひな形）。
2. **重大度を決める**（§1）。
3. **封じ込める**（§3）。原因が分からなくても、広がるのを先に止める。
4. **証拠を残す**（§4）。ログは短い期間で消えるものがある。**何も消さない。**
5. S1・S2 は、**連絡する**（§5）。

## 3. 封じ込め

当てはまるものだけ行う。**すべてオーナーが実行する。**

### API を止める（メンテナンス）

```bash
cd app/web
node scripts/ops.mjs maintenance on "ただいまメンテナンス中です"   # 約 10 秒で全 API に反映
node scripts/ops.mjs maintenance status
node scripts/ops.mjs maintenance off                              # 戻す
```

- 止まるのは API だけ（503 を返す。管理者と、ログイン・Worker の webhook は通る）。写真の投稿・登録・プロフィールの変更などが止まる。**ブラウザから Firestore を直接読む・書く操作（タイムラインの表示、文字だけの投稿、コメント、いいね）は止まらない。画面に「メンテナンス中」と出す仕組みも無い**（API の失敗時に、この文言が出るだけ）。
- 読み書きごと止めたいときは、下の「アクセスを遮断する」か、Rules を全拒否にする（Terraform の apply が要る。時間がかかる）。

### 特定の人を止める

- 管理画面でそのゲストのタグを外す・承認を取り消す → `applyGuestTags()` が Custom Claims を変え、`revokeRefreshTokens` でログインを切る（反映は、手元のトークンの期限まで最長 1 時間。API は失効チェックがあるのですぐ止まる）。
- 投稿は、管理画面で非表示にする（消さない。証拠になる）。

### 秘密を失効させる

漏れた・漏れたかもしれない秘密は、[rotation-runbook.md](../security/rotation-runbook.md) の「漏れたとき」のとおり、**新しい値を登録してから古い値を失効**させる。急ぐとき（使われている形跡があるとき）だけ、先に失効させる（本番は止まる。メンテナンス表示を先に出す）。

| 漏れたもの | すぐやること |
|---|---|
| サービスアカウントの鍵 | `gcloud iam service-accounts keys disable <鍵の ID> --iam-account=<サービスアカウント>` → runbook §1 |
| R2 のトークン | Cloudflare の管理画面で失効 → runbook §2。原本が消されていないかを見る |
| Worker の webhook の秘密 | runbook §3（対の値。両方変える） |
| 合言葉（パスコード） | runbook §7。未承認の一覧に、知らない登録が無いかを見る |
| 運用アカウント（GitHub・Google・Vercel・Cloudflare など） | パスワードを変え、全セッションを切り、MFA を付け直し、トークンをすべて失効。**そのアカウントから触れる秘密は、全部漏れたものとして入れ替える** |

### アクセスを遮断する

- Vercel の管理画面 → Firewall: 攻撃元の IP の遮断、Attack Mode（全員にチャレンジを出す）。Worker の webhook（`/api/hooks/`）と LINE のリンクプレビューを止めない設定に注意する（CLAUDE.md のルール 19）。
- 不正なコードが `main` に入った: Vercel の管理画面 → Deployments → 正常だったデプロイに戻す。そのうえで、原因のコミットを `git revert` する PR を出す。
- CSP が原因で動かない: [csp-check.md](../security/csp-check.md) §6。

## 4. 証拠を残す

**消さない・上書きしない。**投稿・アカウント・ログ・R2 のオブジェクトは、調べ終わるまで残す。

| 何を | どうやって | 消えるまで |
|---|---|---|
| アプリの監査ログ | `cd app/web && node scripts/ops.mjs audit --limit 200`（`--actor`・`--action`・`--denied`・`--incomplete`）。出力をファイルに保存 | Firestore に 400 日。毎日の写しが GCS（ロック済み）に 400 日 |
| 個人情報の閲覧ログ | `python3 scripts/pii-access-report.py --hours 168`（`--staff`・`--denied`） | 400 日 |
| GCP の管理操作のログ | Cloud Console → Logging。鍵の ID・サービスアカウント・時刻で絞る | 400 日（管理アクティビティ） |
| Vercel の関数のログ | 管理画面 → Logs。**保持が短いので、最初に書き出す**（画面から、該当の時間帯をエクスポートかコピー） | プランによる（短い） |
| Vercel の操作の記録・Firewall | 管理画面 → Activity、Firewall | — |
| Sentry | 該当の issue の URL と、イベントの時刻・`request_id` | プランによる |
| Cloudflare | 管理画面 → Audit Log。Worker は `npx wrangler tail`（さかのぼれない） | — |
| GitHub | リポジトリの Security log、Actions の実行の記録、直近のコミットと PR | — |
| データの直前の状態 | PITR で、事故の直前の時点を別のデータベースに複製する（[backup-restore.md](backup-restore.md) §3-1）。**7 日を過ぎると取れない** | 7 日 |

- 保存したファイルには個人情報が入る。リポジトリにも Issue にも置かない。調べ終わったら、保管する期間を決めて消す。
- `request_id`（エラー表示の「ID: xxxxxxxx」、応答ヘッダの `x-request-id`）で、Sentry・監査ログ・Vercel のログを突き合わせられる。

## 5. 連絡

**連絡先は、パスワードマネージャーの「緊急連絡先」**に置く（新郎新婦、会場の担当者、提供先の会社の窓口、相談する弁護士）。ここには書かない。

### 個人情報の漏えいが疑われるとき

1. 何が・何人分・どの項目が・いつからいつまで、を、分かる範囲で書き出す（分からないことは「不明」と書く）。
2. **報告と本人への通知の義務があるかを確かめる。**個人情報保護法では、要配慮個人情報が含まれる漏えい、不正の目的によるおそれがある漏えいなどは、個人情報保護委員会への報告と本人への通知の対象になりうる。目安として、速報は気づいてからおおむね 3〜5 日以内、確報は原則 30 日以内（不正の目的によるおそれがある場合は 60 日以内）とされている。**このサービスが対象になるか、アレルギーの情報がどう扱われるかを含め、必ず専門家と、個人情報保護委員会（https://www.ppc.go.jp/）の案内で確かめる。**提供先の会社から預かった情報なら、その会社への連絡が先（契約で期限が決まっていることがある）。
3. 本人（ゲスト）へは、事実・影響・こちらの対応・本人にお願いすることを、分かった範囲で早く伝える。分からないことを、分かったように書かない。

### 文面のひな形: ゲスト向け

```text
【大切なお知らせ】（サービス名）について

（日付）、（サービス名）で、（何が起きたか。例: 一部の方の登録情報が、本来見られない方から見られる状態になっていたこと）が分かりました。

■ 対象
（どの情報か。例: お名前、ご回答いただいたアレルギーの情報）
（対象の方: 例: ○月○日〜○月○日に登録された方）

■ 現在の状況
（例: ○月○日 ○時に原因を取り除き、現在は見られない状態です。外部で使われた形跡は、現時点で確認されていません。／確認中です。）

■ お願い
（例: 心当たりのない連絡があった場合は、下記までお知らせください。／特にありません。）

■ お問い合わせ
（連絡先）

ご心配をおかけし、申し訳ありません。分かったことは、あらためてお知らせします。
```

### 文面のひな形: 提供先の会社向け（第一報）

```text
件名: 【第一報】（サービス名）におけるセキュリティ事案のご報告

1. 発覚した日時: 
2. 概要（分かっている事実だけ）: 
3. 影響の範囲（対象の情報・人数。不明な点は「調査中」）: 
4. 原因（判明している範囲）: 
5. 実施した対応（封じ込め・証拠の保全）と、その時刻: 
6. 現在の状況（継続中か、止まったか）: 
7. 今後の予定（次の報告の時刻、調査の内容）: 
8. 連絡先: 

※ 本報は第一報です。事実関係は調査により変わることがあります。
```

## 7. 当日の備え

- 当日の朝に、`python3 scripts/csp-verify.py`、スマホでのログインと写真の投稿、`/screen` の表示を確かめる。
- 監査ログが書けないと更新系の API が止まる（fail-closed）。可用性を優先するなら、`AUDIT_FAIL_OPEN=true` を事前に入れるかを決めておく（入れるなら理由を残す。[secrets-inventory.md](../security/secrets-inventory.md) §3）。
- 当日は、原因の調査より**動かし続けること**を優先する。API の停止・デプロイの巻き戻し・投稿の非表示までにとどめ、鍵の入れ替えのような大きな作業は、漏えいの形跡が無い限り、終わってから行う。
- 手元に置くもの: パスワードマネージャー、MFA の端末、回復コード、この手順書（オフラインで読める形）。
