# 削除の手順書（Issue #105）

最終更新: 2026-10-12

ゲストから「自分のデータを消してほしい」と言われたとき、何を・どの順で・どこから消すか。イベントのあとの一括の削除と保持の選択肢も、ここに書く。何がどこにあるかは [data-inventory.md](data-inventory.md)。

- **ここに書いた操作は、すべてオーナーが実行する**（消す操作は取り消せない。Claude Code がしてよいのは、読み取りの確認まで。CLAUDE.md ルール 18）。
- **この手順は、まだ通しで試していない。**招待状を配る前に、テスト用のゲストで §2 を 1 回通し、気づいたことをここに直す（§6 に記録）。
- このリポジトリは公開されている。依頼した人の名前・連絡先・uid を、このファイルにも Issue にも PR にも書かない。記録は §5 の形で、リポジトリの外に置く。
- 開示・訂正・削除の依頼に法的な期限や義務があるかは、ここでは判断していない。専門家に確かめる。

## 1. 依頼を受けたら

1. **本人からの依頼かを確かめる。**LINE のトークや対面など、本人だと分かる経路で受ける。知らないアドレスからのメールだけで消さない（他人のデータを消させる嫌がらせを防ぐ）。
2. **何を消すかを決める。**次のどれかを本人に確かめる。

   | 依頼 | すること |
   |---|---|
   | 特定の投稿・コメントだけ | 本人が画面から消せる（投稿の「削除」、コメントの「削除」）。**写真のファイルまで消してほしいときは** §2 の手順 6 だけを、その投稿の分について行う |
   | 回答（アレルギー・備考）を直したい・消したい | 本人が `/guide/questionnaire` から直せる（空にできる） |
   | 自分が写っている、ほかの人の写真 | §3 |
   | **アカウントごと全部** | §2 |

3. **すぐには消えないものを伝える**（§2 の最後の表）。バックアップは最長 14 週、監査ログは 400 日残る。
4. 出欠の管理に本名が要る期間（披露宴の前）に「全部」を頼まれたら、**出席の取り消しとして扱うか**を本人と確かめる（名簿から消えると、席と料理の手配から漏れる）。

## 2. ゲスト 1 人のデータをすべて消す

準備:

```bash
bash scripts/ensure-gcloud-auth.sh
```

- 対象の uid（`line:U…`）を、管理画面のゲスト一覧で確かめる。**仮登録（`pre_…`）から付け替えた人は、`mergedInto` がその人を指す `pre_…` の文書も対象**（`guests`・`guestPrivate`・`guestAdmin` の 3 つ）。
- 下の「コンソール」は Firebase コンソールの Firestore。**データベースは `(default)`。**
- 順番を守る（先にログインを止める。先にデータだけ消すと、本人の端末から書き足されることがある）。

| # | 何を | どこで | 手順 |
|---|---|---|---|
| 1 | ログインを止める | 管理画面（`/admin/guests`） | 対象のゲストを「アクセス停止」にする。タグが空になり、ログイン中のセッションが失効する |
| 2 | 消すものを数える | コンソール | `posts` を `authorUid == <uid>` で絞り、投稿の ID と、各投稿の `media[].storagePath`・`media[].originalPath`（R2 のキー）を控える。`faces` を `matchedGuestId == <uid>` で絞り、`awsFaceId` が入っているものを控える（手順 7 で使う）。控えはリポジトリの外に置き、終わったら消す |
| 3 | 投稿を消す | コンソール | 手順 2 の投稿を、1 件ずつ「ドキュメントを削除」（サブコレクションのコメント・いいねも一緒に消す）。そのあと `faces` を `postId == <投稿の ID>` で絞り、残っていれば消す |
| 4 | ほかの人の投稿に付けたものを消す | コンソール | コレクション グループ `comments` を `authorUid == <uid>` で絞って消す（親の投稿の `commentCount` は 1 ずつ減らす。減らさないと、数だけが合わなくなる）。`episodes` を `authorUid == <uid>` で絞って消す。**いいね（`posts/*/reactions/<uid>`）は、いまの道具では横断して探せない**（下の「まだできないこと」） |
| 5 | 本人の文書を消す | コンソール | `guests/<uid>`・`guestPrivate/<uid>`・`guestAdmin/<uid>`・`notifications/<uid>`（サブコレクション `items` ごと）・`redeemAttempts/<uid>`。`pre_…` の文書があれば、それも |
| 6 | 写真のファイルを消す | Cloudflare の管理画面（R2） | **公開バケット `wedding-media`**: `u/<uid>/` の下すべて（軽量版 `t/`、高画質版 `o/`、アイコン画像）。**非公開バケット `wedding-originals`**: `u/<uid>/` の下すべて（原本）と、`_linked/u/<uid>/`・`_pending/u/<uid>/`・`_failed/u/<uid>/`・`_skipped/u/<uid>/` の下すべて（マーカー）。**消す前に、接頭辞が対象の uid ちょうどであることを 2 回確かめる**（R2 にはバージョニングが無く、消したら戻せない） |
| 7 | 顔の特徴データを消す | AWS（CLI か管理画面） | 下のコマンド |
| 8 | 参照用の顔写真を消す | Google Cloud コンソール（Cloud Storage。旧バケット） | `reference_faces/<uid>/` の下すべて。**バージョニングが有効なので、「非現行バージョンを表示」にして旧版も消す** |
| 9 | ログインのアカウントを消す | Firebase コンソール（Authentication） | 対象の uid のユーザーを削除する（LINE の表示名とアイコンの URL、Custom Claims が消える） |
| 10 | ほかの人のデータに残った印を消す | コンソール | `faces` を `matchedGuestId == <uid>` で絞り、`matchedGuestId` を `null` に、`awsFaceId` を空にする（ほかの人の写真に写っていた記録）。`posts` を `detectedUserIds array-contains <uid>` で絞り、配列から外す。`posts` を `mentionUids array-contains <uid>` で絞り、配列から外す（本文に残った `@ニックネーム` の文字は、投稿者の文章なので、消すかどうかを本人と決める） |
| 11 | 確かめる | コンソール・各管理画面 | 手順 2〜10 の絞り込みを、もう一度かけて 0 件であること。R2 の接頭辞が空であること。公開の URL を 1 つ開き、見えなくなったこと（キャッシュ: 下の注意） |
| 12 | 記録する | リポジトリの外 | §5 |

**手順 7（Rekognition）のコマンド**（コレクションの名前は既定で `wedding-faces`。リージョンは Vercel の環境変数 `REKOGNITION_REGION` / `AWS_REGION` と同じにする）:

```bash
aws rekognition list-faces --collection-id wedding-faces --region <REGION> \
  --query "Faces[?ExternalImageId=='<uid>'].FaceId" --output text
# 出てきた FaceId を、まとめて消す
aws rekognition delete-faces --collection-id wedding-faces --region <REGION> --face-ids <FaceId> <FaceId> ...
# もう一度 list-faces をかけて、空になったことを確かめる
```

- 顔の特徴には uid（`ExternalImageId`）が付いている。`list-faces` は 1 回に返す件数に上限があるので、`NextToken` が返ったら続きも見る。

**注意**

- **公開バケットのキャッシュ:** 高画質版は `Cache-Control: immutable`（1 年）で配っている。R2 から消しても、Cloudflare のキャッシュと、すでに見た人のブラウザには残りうる。消したあと、Cloudflare の管理画面で該当の URL（または接頭辞）のキャッシュを消す。**すでに保存された・スクリーンショットされた写真は、回収できない**（そのことを本人に伝える）。
- **ゲストの端末:** まだ送っていない原本は、本人の端末の中にある。運営からは消せない（本人がサイトのデータを消す）。
- **もう一度ログインされたとき:** アカウントを消しても、同じ LINE アカウントでログインすれば、新しい未承認のアカウントとして作り直される（データは空）。承認しなければ、何も見えない。

**すぐには消えないもの（本人に伝える）**

| 残るもの | いつまで | 中身 | 理由 |
|---|---|---|---|
| Firestore のバックアップ | PITR 7 日・日次 7 日・**週次 14 週** | 消す前のすべて（本名・アレルギーを含む） | バックアップから 1 人分だけを消す方法が無い。期限で自動的に消える。**この間に復旧（[../ops/backup-restore.md](../ops/backup-restore.md)）をしたら、消した人のデータを戻さない**（§5 の記録と突き合わせて、もう一度消す） |
| 監査ログ（Firestore と GCS の写し） | 400 日 | uid・操作の種類・日時・項目の名前・仮名にした IP。**本名や回答の値は入っていない** | 改ざんできない記録として持つ。GCS はロック済みで、誰にも消せない |
| 個人情報の閲覧ログ（Cloud Logging） | 400 日 | 誰がいつ読んだか。読んだ人の uid と LINE の表示名 | 不正な閲覧の調査のため。消す必要があるときは、オーナーが GCP で消す（ロックするまでは消せる） |
| Sentry・Vercel・Cloudflare のログ | 各サービスの保持期間 | エラーとアクセスの記録。本名・回答は送っていない | 自動で消える |

**まだできないこと（別 Issue の候補）**

- **ほかの人の投稿に付けた「いいね」を、横断して探せない。**文書は `posts/{投稿}/reactions/{uid}` にあり、コンソールでは投稿を 1 つずつ開くしかない。残るのは「絵文字・uid・日時」だけだが、uid が残る。
- **手順 3〜5・10 は、件数が多いと手作業では危ない。**1 人分を、先に一覧（dry-run）してから消す運用スクリプト（`app/web/scripts/delete-guest.mjs`。既定は一覧だけ、`--execute` を付けたときだけ消す）を作れば、「いいね」も含めて 1 回で済む。**作るかどうかは未決定**（消すスクリプトを置くこと自体がリスクなので、オーナーが決める）。

## 3. 自分が写っている、ほかの人の写真

1. 対象の投稿を確かめる（本人に画面で示してもらう）。
2. 投稿者に連絡し、投稿者本人に消してもらう（または写真を差し替えてもらう）。応じてもらえない・連絡がつかないときは、管理者が非表示にする（管理画面。`/api/admin/posts/visibility`）。非表示は削除ではない（データは残る。ゲストとスクリーンからは見えなくなる）。
3. 写真のファイルまで消すときは、§2 の手順 6 を、その写真のキーだけについて行う（投稿の `media[].storagePath`・`originalPath`。原本のマーカーも）。
4. 顔の記録（`faces` の `matchedGuestId`）と、Rekognition に登録した特徴（`awsFaceId`）があれば、§2 の手順 7・10 と同じように消す。

## 4. イベントのあと（保持と一括の削除）

**保持期間は未決定（オーナーが決める）。**決めたら、[privacy-policy-draft.md](privacy-policy-draft.md) の「保存期間」と、この節を直す。

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A. 期間を決めて、すべて消す | 披露宴の N か月後（例: 3 か月）に、下の「一括の削除」を行う。写真は、その前に新郎新婦の手元へ退避する | 説明が単純。預かる期間が短い | ゲストが、あとから写真を見返せなくなる（先に「◯月◯日まで」と告知して、保存してもらう） |
| B. 段階的に消す | 披露宴の直後（例: 1 か月以内）に、**アレルギー・備考・送金の状態・顔の記録・Rekognition のコレクション・原本の EXIF つきファイル**を消す。写真と投稿は、もう少し長く（例: 1 年）残す | 扱いに気をつける情報を、早く手放せる。写真は見返せる | 手順が 2 回になる。残す期間中の運用（鍵のローテーション・監視）が続く |
| C. 期限を決めずに残す | アルバムとして、新郎新婦が消すと決めるまで残す | 手間が無い | 「いつまで」を説明できない。漏えいのリスクと運用が、終わらない。法人への提供では説明がつきにくい |

提案: **B。**アレルギーと顔の記録は、披露宴が終われば使い道が無い。

**一括の削除（すべてを消すとき）の順番**

1. 告知する（いつ消すか。写真を保存する期限）。
2. メンテナンスにする（`cd app/web && node scripts/ops.mjs maintenance on`）。ブラウザから Firestore に直接書く操作は止まらないので、全員のタグを外すか、Rules を閉じる（[../ops/incident-response.md](../ops/incident-response.md) §3）。
3. 新郎新婦の手元に残すもの（写真・メッセージ）を退避する。退避先の保管と期限も決める（手元に移っても、預かった個人情報であることは変わらない）。
4. Rekognition のコレクションを消す（`aws rekognition delete-collection --collection-id wedding-faces --region <REGION>`）。
5. R2 の 2 つのバケットを空にする（原本 → マーカー → 公開）。Worker を止める（Cron を外す）。
6. Firebase Storage の旧バケットの `reference_faces/` を、旧版ごと消す。
7. Firestore のコレクションを消す（`guests`・`guestPrivate`・`guestAdmin`・`posts`（サブコレクションごと）・`faces`・`episodes`・`notifications`・`redeemAttempts`）。**`auditLogs` は消さない**（TTL で消える。GCS の写しは 400 日のロック）。
8. Firebase Authentication のユーザーを消す（管理者のアカウントは、最後に）。
9. 定期バックアップのスケジュールを止める（`infra/terraform/backup.tf`。**止めないと、空のデータベースのバックアップが続くだけだが、止める前のバックアップは最長 14 週残る**）。
10. 鍵とトークンを失効させる（[../security/rotation-runbook.md](../security/rotation-runbook.md) の各節の「失効」）。Sentry のプロジェクト、Vercel のプロジェクト、LINE のチャネルを閉じるかを決める。
11. 14 週後に、バックアップが残っていないことを確かめる。監査ログの GCS バケットは、最後の記録から 400 日たつまで消せない（プロジェクトごと閉じる場合の扱いは、そのときに GCP の資料で確かめる）。

- Firestore のデータベース・R2 の原本には、削除保護と「消さない」ルール（CLAUDE.md ルール 18、Terraform の `prevent_destroy`）がある。**一括の削除は、オーナーが明示して決めたときだけ**行い、ルールと Terraform の変更は、そのための PR で行う。
- B の第 1 段階（アレルギーなどだけを消す）は、`guestPrivate` の該当の項目を空にする運用スクリプトが要る。作るのは、保持期間が決まってから。

## 5. 記録（リポジトリの外に置く）

依頼ごとに、次を残す（パスワードマネージャーのメモなど。**このリポジトリには書かない**）。

- 受けた日、本人確認の方法、依頼の内容（全部／一部）
- 実行した日、実行した手順の番号、各手順で消した件数
- 消した uid（**バックアップの期限が切れるまで持つ**。復旧したときに、もう一度消すため。14 週たったら、この記録からも uid を消す）
- 本人に伝えた内容（すぐには消えないもの）と、伝えた日
