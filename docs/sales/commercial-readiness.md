# 商用で提供する前に決めること（Issue #106）

最終更新: 2026-10-13（Vercel の料金と条件は、同日に公式の資料で確かめた。**変わるので、変える前に見直す**）

ブライダルプロデュース（BP）会社などの法人に提供する前に要る、ホスティング・契約・ヒアリングの整理。**決めるのはオーナー。**契約と法律に関わることは、専門家に確かめる前提で、論点だけを並べる。

このリポジトリは公開されている。**相手の会社名・担当者・連絡先・見積もり・ヒアリングの回答は、ここに書かない**（非公開のメモに置く）。

## 1. ホスティング（Vercel のプラン）

### いまのプランでは、商用で提供できない

Vercel の公式の資料（[Fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines) の「Commercial usage」）:

- Hobby は、**非商用の個人利用だけ**。商用の利用には、Pro か Enterprise が要る。
- 商用とは、制作に関わる**誰か**の金銭的な利益のために使われるデプロイのこと。例として、「サイトの作成・更新・ホスティングの対価を受け取る」「商品やサービスの販売の宣伝」「訪問者への支払いの要求・処理」が挙がっている。
- 当てはまるか分からないときは、Vercel のサポートに聞く。

→ 自分たちの披露宴のために使う、いまの形は非商用。**対価を受け取って提供する・提供のために作り込む時点で、Pro 以上が要る。**対価の無い試用（デモを見せるだけ）がどちらに当たるかは、Vercel のサポートに確かめる。

### Pro に変えると変わること

| 項目 | Hobby（いま） | Pro | 出どころ |
|---|---|---|---|
| 商用の利用 | 不可 | 可 | [Fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines) |
| 料金 | 無料 | **月 20 ドル**（デプロイできる席 1 つと、月 20 ドルぶんの利用枠を含む。超えたぶんは従量。税は別） | [Pro plan](https://vercel.com/docs/plans/pro-plan) |
| メンバー | 1 人 | デプロイできる席は 1 つ月 20 ドルで追加。閲覧だけの席は無料・無制限 | 同上 |
| 関数のログの保持 | 1 時間 | 1 日（有料の Observability Plus で 30 日） | [Runtime Logs](https://vercel.com/docs/logs/runtime) |
| 第三者診断 | 不可 | 可（大量のリクエストを伴うものは Enterprise だけ） | [Penetration testing on Vercel](https://vercel.com/kb/guide/penetration-testing-on-vercel) |
| Firewall の「一定時間の遮断」（Persistent Actions） | 不可 | 可 | [WAF Custom Rules](https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules) |
| SAML SSO（運用者のログイン） | — | 追加で月 300 ドル | [Pro plan](https://vercel.com/docs/plans/pro-plan) |
| 稼働率の保証（SLA） | 無い | **Pro での有無は確かめていない**（Enterprise の契約事項のことが多い） | — |

**確かめられなかったこと（変える前に、料金のページと管理画面で見る）:** プランごとの Firewall のカスタムルールの数の上限、レート制限のルールの数と料金、チームの役割（RBAC）の細かさ、Preview のアクセス保護の種類、利用量の上限を超えたときの動き。

### 変えたあとに見直すもの

| 見直すもの | なぜ |
|---|---|
| Firewall のルール（CLAUDE.md ルール 19） | ルールの数や機能の制約がゆるむ。`api-flood-guard` に一定時間の遮断を足すか、ログだけにしている `bot-protection` を上げるか。**Worker の webhook（`/api/hooks/`）と LINE のリンクプレビューを止めない**条件は変わらない |
| 利用量の上限と通知（Spend Management） | 従量の課金になる。外から大量に呼ばれたときの上限を、先に決める。画像の最適化を使わない設定（ルール 9）は、課金を外から増やされないために、そのまま保つ |
| ログの保持 | 1 日で足りるか。事故の調査には短い（[incident-response.md](../ops/incident-response.md) §4）。Observability Plus か、ログの外部への転送を足すか |
| 関数のリージョン | データベース（東京）に近づけるか。いまの場所は未確認（[data-inventory.md](../privacy/data-inventory.md) §7） |
| メンバーと権限 | 閲覧だけの席を、提供先やレビュアーに渡すか（[certification-roadmap.md](certification-roadmap.md) §4） |
| 文書 | `CLAUDE.md` の「Vercel Hobby」の記述と、ルール 9・17・19 の前提。[security-answers.md](security-answers.md) の「ホスティング」「ログの保持」 |

### いつ変えるか（選択肢）

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A. いますぐ | 営業を始める前に変える | 規約の線引きで迷わない。診断と検証環境の準備を、すぐ始められる | 提供が決まる前から、月 20 ドル（と従量） |
| B. 提供が決まる前の、準備の段階で | BP 会社に見せるデモ・検証環境・診断の準備を始めるとき | 費用が、準備の開始と揃う | 「準備」と「営業」の境目を、自分で決める必要 |
| C. 契約の直前 | 対価を受け取る直前 | 費用がいちばん小さい | 診断・検証環境・Firewall の見直しが、契約の間際に集中する。デモの段階が規約に触れないかを、サポートに確かめる必要 |

**提案: B。遅くとも、診断の見積もりを取る前。**月 20 ドルは、迷う時間より小さい。

### 検証用の環境を分けるか

いまは、手元のエミュレーターだけ。Vercel の Preview には本番の秘密を入れていないので、ログイン・写真の投稿は動かない（[secrets-inventory.md](../security/secrets-inventory.md) §4）。

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A. 分けない（いまのまま） | 画面はエミュレーター、通しの確認は本番 | 手間が無い | 診断を、実在のゲストのデータがある本番で行うことになる。法人に「検証環境はあるか」と聞かれたら「無い」 |
| B. 別の Firebase プロジェクト + Vercel の Preview | 検証用の GCP / Firebase プロジェクト・R2 のバケット・LINE のチャネルを作り、Preview の環境変数にその秘密を入れる | 本番と同じ経路を、作りもののデータで通せる。診断の対象にできる。デモにも使える | 管理する秘密と設定が 2 倍になる（一覧・ローテーション・Terraform の変数）。Firebase の API キーのリファラー制限・LIFF の URL・CSP の許可も、環境ごとに要る |
| C. 式ごとにプロジェクトを分ける設計と一緒に考える | 複数の式で使う設計（Issue #107）で「式ごとに別のプロジェクト」を選ぶなら、検証環境はその 1 つとして作れる | 設計が 1 回で済む | #107 の結論を待つことになる |

**提案: 診断か、法人への提供のどちらかを決めた時点で B。**それまでは A。#107 でプロジェクトを分ける案を選ぶなら、C として一緒に作る。

## 2. 契約・体制（論点の整理。専門家に確かめる前提）

法人に提供するなら、何かしらの文書が要る。**どれが要るか・何を書くかは、相手の求めと、専門家の確認で決める。**ここには、聞かれること・決めること・いまある材料だけを書く。

| 文書 | 要りそうか（見立て） | 決めること | いまある材料 |
|---|---|---|---|
| 利用規約（法人向け・ゲスト向け） | 要る | 誰と誰の契約か（運営者と BP 会社／新郎新婦／ゲスト）。禁止事項、アカウントの停止、提供の終了、知的財産（ゲストの写真の権利は誰に）、免責と責任の上限、準拠法 | 無い |
| SLA（サービスレベル） | 求められることが多い。**約束できる範囲で** | 稼働率の目標（約束か、努力目標か）、対象の時間（披露宴の当日だけ手厚くするか）、サポートの受付の時間と返信の目安、障害時の連絡の方法と時間、計画的な停止の告知 | 稼働率の実績は測っていない。復旧の目安は [backup-restore.md](../ops/backup-restore.md) §2（約束できる値ではない）。運営者 1 名で、24 時間の対応はできない。利用している各社の障害は、こちらでは直せない |
| 責任の範囲 | 要る | どこまでが運営者の責任か（アプリと設定）、どこからが各社のサービスか、相手（BP 会社・新郎新婦）が行うこと（ゲストの承認、タグの設定、投稿の管理） | [subprocessors.md](../privacy/subprocessors.md)、[security-overview.md](security-overview.md) §2 |
| 個人情報の取り扱い（委託契約・覚書） | 要る可能性が高い | BP 会社がゲストの個人情報を預かる立場なら、運営者はその委託先になりうる。その場合に聞かれること: 取り扱う情報と目的、再委託先（外部のサービス）の一覧と事前の承諾、日本の外での取り扱い、安全管理の措置、事故のときの報告の期限、監査への協力、終了時の返却・消去とその証明 | [data-inventory.md](../privacy/data-inventory.md)、[subprocessors.md](../privacy/subprocessors.md)、[deletion-runbook.md](../privacy/deletion-runbook.md)、[incident-response.md](../ops/incident-response.md) §5。**保存期間は未決定** |
| プライバシーポリシー（ゲスト向け） | 要る | 誰の名前で出すか（運営者／BP 会社／新郎新婦）。顔の検出の扱いと同意、保存期間、問い合わせ先 | [privacy-policy-draft.md](../privacy/privacy-policy-draft.md)（未承認） |
| 秘密保持（NDA） | 相手による | セキュリティの回答や診断の報告書を渡す前に結ぶか | — |
| 料金・支払い | 要る | 課金の単位（式ごと・年額・ゲストの数）、当日だけ増える費用（音声合成の GPU など）の扱い | Issue #107 の検討項目 |

**先に決めないと、どの文書も書けないこと**

1. **提供する主体。**個人のままか、法人にするか。相手の取引の基準（個人との契約ができるか、反社チェック、支払いの条件）に関わる。認証の条件でもある（[certification-roadmap.md](certification-roadmap.md) §3）。
2. **提供の形。**運営者が式ごとに環境を用意して運用まで行うのか、BP 会社の担当者が管理画面を使うのか。責任の範囲・権限・サポートが変わる（Issue #107）。
3. **約束できないことを、約束しない。**24 時間の対応、稼働率の保証、国内だけでの保管、即日の完全な削除（バックアップに最長 14 週、監査ログは 400 日残る）は、いまの作りと体制ではできない。

## 3. BP 会社へのヒアリング項目

最初の打ち合わせで聞くこと。**答えは、公開されない場所に控える。**先に [security-overview.md](security-overview.md) を渡し、「未取得・未実施」のことを伝えてから聞く。

### 利用の形

- [ ] どの場面で使うか（披露宴の当日だけ／準備の期間から／式のあともアルバムとして）
- [ ] 1 年に何件の式で使う見込みか。同じ時期に重なる件数
- [ ] 1 つの式のゲストの数（ふつう・最大）。当日に同時に使う人数
- [ ] 誰が操作するか（BP 会社の担当者／新郎新婦／会場のスタッフ）。担当者は何人で、式ごとに分かれるか
- [ ] ゲストは LINE でログインする前提でよいか。LINE を使わないゲスト（年配の方・海外の方）への対応が要るか
- [ ] 会場での投影（プロジェクター）を使うか。会場の回線と機材は誰が用意するか

### 必要な機能

- [ ] 要る機能の優先度（招待状と出欠／アレルギーなどの回答／写真の投稿とタイムライン／会場の投影／顔の検出／AI・音声の演出）
- [ ] **顔の検出は要るか**（要らないなら外せる。扱う情報が減り、説明が軽くなる）
- [ ] 既存の仕組みとのつなぎ（招待客の名簿の取り込み・出欠の書き出しの形式。席次や引き出物のシステムなど）
- [ ] 見た目の変更（会社や式ごとのロゴ・色・文言）
- [ ] 担当者のログインの方式（LINE でよいか。会社のアカウントでの SSO が要るか）
- [ ] 担当者の権限の分け方（すべてできる／閲覧だけ／式ごと）

### セキュリティと個人情報

- [ ] 導入の前に出す資料は何か（会社の様式のチェックシート／自由な形式の説明／診断の報告書）。様式があれば、先にもらう
- [ ] **認証（ISMS・プライバシーマーク）は、導入の条件か。**条件でない場合、代わりに何があれば足りるか
- [ ] **第三者診断は、条件か。**指定の診断会社・報告書の形式・実施の時期はあるか
- [ ] 個人の運営者・開発者との取引はできるか（法人であることが条件か）
- [ ] データの保管場所の条件（日本の中だけ、など）。日本の外のサービスの利用は認められるか
- [ ] 外部のサービス（再委託先）について、事前の承諾や届け出が要るか
- [ ] AI のサービスに、ゲストの情報や写真を送ることへの方針
- [ ] ゲストの個人情報は、誰が取得する立場か（BP 会社／新郎新婦）。ゲストへの説明と同意は、誰の名前で行うか
- [ ] 式のあと、データをいつまで残したいか。消したことの証明は要るか。新郎新婦への写真の引き渡しの形
- [ ] 事故のときの連絡の条件（窓口・期限）
- [ ] 操作の記録（監査ログ）を、BP 会社の側で見たいか

### 契約と運用

- [ ] 契約の形（業務委託／利用契約／式ごとの発注）と期間
- [ ] 料金の考え方（式ごと・年額・ゲストの数）と、支払いの条件
- [ ] 稼働率・サポートの時間の期待（とくに、披露宴の当日。土日・祝日の対応）
- [ ] 当日の立ち会いは要るか（現地／遠隔）
- [ ] 障害のときの責任と補償についての、会社の標準の条件
- [ ] 秘密保持の契約は要るか
- [ ] 始めたい時期。試しに使う式の候補

### 聞いたあとに決めること

ヒアリングの答えで、次が決まる: Pro に変える時期（§1）、検証環境（§1）、診断と認証（[certification-roadmap.md](certification-roadmap.md) §5）、複数の式で使う設計の優先度（Issue #107）、保存期間（[deletion-runbook.md](../privacy/deletion-runbook.md) §4）。
