# 法人利用に向けた設計の検討（Issue #107）

最終更新: 2026-10-13（コード・Rules・Terraform の現状から作成。**実装はしていない**）

ブライダルプロデュース（BP）会社が複数の式で使う、または複数の会社に提供するときに、何を作り直す必要があるか。論点ごとに、選択肢と提案を書く。**決めるのはオーナー。**決まったら、実装が要るものを別の Issue に分ける（§10）。

- 関連: 法人向けの回答集と準備は [../sales/](../sales/)（とくに [commercial-readiness.md](../sales/commercial-readiness.md) §3 のヒアリング項目。**この検討の多くは、ヒアリングの答えで結論が変わる**）。
- このリポジトリは公開されている。相手の会社名・契約の条件は書かない。
- 外部のサービスの仕様・料金・SLA のうち、今回確かめきれなかったものは「要確認」と書いた。

## 0. 結論（提案の要約）

| 論点 | 提案 | 区分 |
|---|---|---|
| テナントの分離 | **式ごとに、環境をまるごと分ける**（Firebase / GCP プロジェクト・R2 のバケット・Vercel のプロジェクト）。同じプロジェクトの中で `tenantId` で分ける方式は、いまは作らない | 必須（分け方を決めること）／見送り（同一プロジェクト内の分離） |
| タグによるアクセス制御 | 式の中の「見える範囲」としては、そのまま使える。**式と式の境界には使えない** | — |
| 管理者の権限 | 「新郎新婦（全権）」と「BP 会社の担当者」を分ける。まず**閲覧だけ**と**担当者**の 2 つを足す | 必須（担当者が管理画面を使う場合） |
| 監査ログの閲覧 | 当面は、運営者が依頼に応じて書き出す。担当者の役割を作ったあとで、管理画面に読み取り専用の一覧を足す | 推奨 |
| 認証 | ゲストは LINE のまま。担当者は、要望があれば Google か Microsoft のアカウントでのログインを足す。SAML の SSO は作らない | 推奨（担当者のログイン）／見送り（SAML） |
| 可用性 | 稼働率は約束しない。先に、外からの死活監視・通知・引き継ぎ先を整える。複数リージョン化はしない | 必須（監視と通知）／見送り（複数リージョン） |
| 課金の単位 | **式ごと**を前提にする（環境を式ごとに分ける方式と、費用の見え方が合う）。アプリの中に課金の仕組みは作らない | 見送り（アプリ内の課金） |

**先に決めること:** 提供の形（運営者が式ごとに環境を用意して運用まで行うのか、BP 会社の担当者が管理画面を使うのか）。これで、権限・ログの閲覧・担当者の認証が「必須」か「不要」かが決まる。

## 1. いまの作りが「1 つの式」を前提にしている箇所

設計を変えるときに触ることになる場所。分離の方式（§2）によって、変える量が大きく違う。

| 場所 | いまの作り | 根拠 |
|---|---|---|
| データベース | コレクションが最上位に並ぶ（`guests`・`guestPrivate`・`guestAdmin`・`posts`・`faces`・`episodes`・`tags`・`notifications`・`auditLogs`・`rateLimits`）。式や会社を表す項目は無い | `infra/firestore/firestore.rules` |
| 権限（Custom Claims） | `tags`（配列）と `admin`（真偽）だけ。どちらも、プロジェクト全体で 1 つ | `src/lib/guests-server.ts` |
| 管理者 | `admin === true` は「新郎新婦」で、すべてを読み書きできる。付けるのは手元のコマンドだけ | `app/web/scripts/make-admin.mjs` |
| uid | `line:<LINE のユーザー ID>`。LINE のユーザー ID は、LINE のプロバイダーごとに決まる | `src/app/api/auth/line/route.ts` |
| 招待状の中身 | 新郎新婦の名前・日時・会場が、サーバー専用のソース（`src/config/wedding.ts`）に書いてある | 同左 |
| 合言葉 | 環境変数 `WEDDING_PASSCODE` が 1 つ | `src/lib/passcode-server.ts` |
| タグの語彙 | 組み込みタグ（全員・親族・新郎友人…）はソースに固定。カスタムタグは `tags` コレクション | `src/config/tags.ts` |
| 投影（`/screen`） | 出すタグは、ビルド時の環境変数 `NEXT_PUBLIC_SCREEN_TAGS` | `src/config/screen.ts` |
| 写真 | R2 のバケットは 2 つで固定。キーは `u/{uid}/{t\|o}/…`（式を表す部分は無い） | `src/lib/r2-server.ts`、`wrangler.toml` |
| Worker | バケット名・公開の URL・webhook の URL が `wrangler.toml` に固定 | `infra/workers/exif-stripper/wrangler.toml` |
| 顔の照合 | Rekognition のコレクションは 1 つ（既定 `wedding-faces`） | `src/lib/rekognition.ts` |
| メンテナンスの切り替え | `config/runtime` が 1 つ（全体が止まる） | `src/lib/runtime-config.ts` |
| ブラウザの設定 | Firebase の設定・LIFF の ID・写真の配信元・Sentry の DSN が、ビルド時に焼き込まれる（1 つのデプロイ = 1 つの Firebase プロジェクト） | `NEXT_PUBLIC_*` |
| インフラ | Terraform は 1 つのプロジェクトを対象にする（`project_id` は変数）。state はローカル | `infra/terraform/` |
| 保持と削除 | 式が終わったあとの一括の削除は「すべてを消す」手順 | [deletion-runbook.md](../privacy/deletion-runbook.md) §4 |
| CTF の名残 | `ctf_*` のタグと、Rules の `challenges`・`solves`（保留中の機能） | `src/config/tags.ts`、`firestore.rules` |

## 2. テナントの分離

「テナント」は、ここでは**式**（1 つの披露宴）を指す。会社は、式をいくつか持つ上の単位。

### 選択肢

| | A. 式ごとに環境を分ける | B. 同じプロジェクトで `tenantId` で分ける | C. 同じプロジェクトで、式ごとにデータベースを分ける |
|---|---|---|---|
| 中身 | 式ごとに、GCP / Firebase プロジェクト・R2 のバケット・Worker・Vercel のプロジェクト・LIFF・サブドメインを作る。コードは同じリポジトリ | すべてのデータを `tenants/{tenantId}/…` の下に移し、Claims に式の ID を持たせ、Rules のすべての `match` で確かめる | Firestore の名前つきデータベースを式ごとに作る。ログインのアカウント（Firebase Authentication）は共通 |
| 分離の強さ | **強い。**Rules や API の不具合があっても、ほかの式のデータには届かない（資格情報も別） | Rules と API の正しさに頼る。**1 か所の漏れが、ほかの会社への漏えいになる** | データは分かれるが、ログインのアカウントと Claims は共通。サーバーの鍵は全部に届く |
| いまのコードの変更 | **小さい。**式ごとの設定を外に出す（§1 の招待状・合言葉・投影のタグ）と、環境を作る手順の自動化 | **大きい。**Rules・すべてのクエリ・すべての API・R2 のキー・監査ログ・レート制限・顔の照合・テスト（約 310 ケース）を書き直す。既存データの移行も要る | 中くらい。クライアントとサーバーの接続先を式ごとに切り替える。Claims を式ごとに持つ形に変える。写真・顔の照合・監査ログは B と同じ課題が残る |
| 運用の負荷 | **式の数に比例して増える。**秘密の一覧・ローテーション・Terraform の適用・バックアップ・アラート・監視・棚卸しが、式の数だけ要る | 1 つぶんで済む | データベースの数だけ、Rules・インデックス・バックアップの適用が要る。ほかは 1 つぶん |
| 事故のリスク | 設定の付け忘れ（ある式だけアラートが無い、古い Rules のまま）。**自動化とチェックリストで抑える** | 式をまたぐ漏えい。1 つの不具合・1 回の誤操作・1 本の鍵で、全部の式に影響 | B より小さく、A より大きい |
| 式の終了 | 環境ごと片づける。「この式のデータは消した」と説明しやすい。**ただし、ロック済みの監査ログの保管場所がある間は、プロジェクトを閉じられない可能性がある（要確認）** | 式のぶんだけを、すべての場所（データベース・写真・顔・ログ・バックアップ）から選んで消す。バックアップからは、式のぶんだけを消せない | データベースは丸ごと消せる。写真とアカウントは選んで消す |
| 障害・復旧 | 式ごとに独立。1 つの式の復元が、ほかに影響しない | 復元は全体が対象。1 つの式だけを戻すには、書き戻しの作業が要る | 式ごとに復元できる |
| 同じゲストが複数の式に出る | 式ごとに別のアカウント（困らない。LINE のプロバイダーが同じなら uid は同じ値になるが、データは別） | 1 つのアカウントに、式ごとのタグを持たせる。Claims の上限（いま 900 バイト）に当たりやすい | B と同じ |
| 担当者が複数の式を見る | 式ごとにログインし直す（URL が別）。一覧する画面は、別に作らないと無い | 1 つの画面で切り替えられる | B と同じ |
| 費用 | 式ごとの利用料が、そのまま見える。固定費（Vercel の席・ドメイン）は、まとめ方による | 1 つにまとまる。式ごとの内訳は、自分で数える | A と B の間 |
| 向いている規模 | 同時に動く式が、数件〜十数件まで | 数十件以上。自分で申し込める形（セルフサービス）にするとき | — |

### 提案: A（式ごとに環境を分ける）

- **いちばん大きい理由は、事故の広がり方。**運営者は 1 名で、人のレビューも無い（[security-answers.md](../sales/security-answers.md) §11）。Rules や API の 1 か所の漏れが「別の会社のゲストの本名とアレルギーが見える」になる方式 B を、いまの体制で安全に保つ自信を、説明できない。
- **いまの守りが、そのまま使える。**Rules とそのテスト、タグ、監査ログ、バックアップ、削除の手順は、1 つの式を前提に確かめてある。A なら、確かめ直すのは「環境を正しく複製できるか」だけになる。
- **法人への説明がしやすい。**「式ごとにデータベースも鍵も別」「終わったら環境ごと片づける」は、チェックシートで聞かれる分離と消去に、そのまま答えになる。
- **弱点は運用の負荷。**式の数だけ、鍵・Terraform・監視が増える。手作業のままでは、3〜4 件めで破綻する。**A を選ぶなら、環境を作る・点検する・片づける手順の自動化が、必須の作業になる**（§10 の 1・2）。
- B への乗り換えは、同時に動く式が十数件を超える見込みが立ってから考える。A で作る「式ごとの設定を外に出す」作業は、B に進むときにも要るので、無駄にならない。
- C は、分離の強さが A に届かず、作り直しは B に近いので、選ばない。

**A で決めること・確かめること**

| 項目 | 内容 |
|---|---|
| Vercel | 式ごとに Vercel のプロジェクトを作る（同じリポジトリ、環境変数が別）。ブラウザの設定がビルド時に焼き込まれるので、1 つのデプロイを複数の式で共有はできない。`main` への push で、全部の式が同時にデプロイされる（当日の式がある日にマージしない決まりが要る） |
| ドメイン | 式ごとのサブドメイン。CSP・Firebase の API キーのリファラー制限・LIFF のエンドポイント・Worker の webhook の URL・`security.txt` が、ドメインに結び付いている |
| LINE | 式ごとに LIFF アプリを作る（同じプロバイダーの下でよいか、会社ごとに分けるかは、BP 会社の名前で出すかどうかで決まる） |
| 写真 | 式ごとに、R2 のバケット 2 つ・Worker・カスタムドメイン。Cloudflare のアカウントは共通でよいか（R2 の API トークンは、バケットごとに絞る） |
| 顔の照合 | 式ごとに Rekognition のコレクション（環境変数で変えられる）。**顔の検出そのものを外す選択肢**も、ヒアリングで聞く |
| Terraform | `project_id` を変えて同じ構成を適用できる形にはなっている。state を式ごとに分け、リモートに置く（いまはローカル 1 つ。[backup-restore.md](../ops/backup-restore.md) §6）。取り消せない設定（監査ログのロック）を、式ごとにいつ行うかの手順が要る |
| 監査ログのロックと、環境の片づけ | 監査ログの保管場所は 400 日のロック。**式の環境を、最後の記録から 400 日は閉じられない前提で、費用と管理を見積もる**（プロジェクトを閉じられるかどうかは、GCP の資料で要確認） |
| 式の台帳 | どの式が・どの環境で・いつまで（開催日・保持の期限・片づけの予定日）を、1 か所で見られる台帳が要る。最初は非公開の表でよい（§8） |
| 秘密の一覧・棚卸し | [secrets-inventory.md](../security/secrets-inventory.md) は 1 つの環境が前提。式ごとの記録を、どこに・どう置くか（公開のリポジトリに、式の一覧を書かない） |

## 3. タグによるアクセス制御は、テナントの分離に使えるか

**使えない。**タグは「1 つの式の中で、誰に見せるか」の語彙で、式と式の境界を守る作りになっていない。

| いまの作り | 式の境界に使うと起きること |
|---|---|
| `all`・`guest` などの組み込みタグは、全員が同じ ID を持つ | 別の式のゲストどうしで、タグが重なる。`visibleToTags` の重なりだけで見えてしまう |
| `guests` は「タグを 1 つ以上持つ人」なら、だれの公開プロフィールも読める（一覧は 200 件まで） | 別の式のゲストの名簿が読める |
| `isAdmin()` は、式を見ずに、すべてを読み書きできる | ある式の新郎新婦が、ほかの式の本名・アレルギー・顔の記録を読める |
| `tags` コレクションは、ログイン済みなら読める | ほかの式・会社のタグの名前が読める |
| Claims の上限は 900 バイト（タグ ID の配列） | 式ごとのタグを 1 つのアカウントに積むと、すぐ上限に当たる |
| コメントの横断の購読（`collectionGroup("comments")`）は、タグの重なりだけで判定する | 式をまたいで、コメントが `/screen` に出る |
| クライアントのクエリは `visibleToTags` の条件だけ | Rules に式の条件を足すと、**すべてのクエリに同じ条件を足さないと、全体が拒否される**（Rules はフィルタではない） |

**分離の方式ごとの扱い**

- **A（式ごとの環境）: タグの仕組みは変えない。**式の中の見える範囲として、いまのまま使う。変えるとよいのは、次の 3 つだけ。
  1. 組み込みタグの語彙（「新郎友人」「会社関係」「二次会」など）を、式ごとに選べるようにするか。カスタムタグの仕組みはあるが、投稿画面などは組み込みタグが前提（`.claude/rules/data.md`）。
  2. `ctf_*` のタグと、Rules の `challenges`・`solves` を、法人向けの環境から外す（保留中の機能。外すかどうかはオーナーが決める）。
  3. 「新郎新婦あて」（`couple`）の投稿は、`isAdmin()` の人にすべて見える。担当者に `admin` を渡すと、新郎新婦あての私信が担当者に読める（§4）。
- **B（同じプロジェクト）を選ぶ場合の変更（参考）:** データを `tenants/{t}/…` の下に移す。Claims を `{ t: 式の ID, tags, role }` にする（1 つのアカウントは 1 つの式。複数の式に出る人は、式ごとに別のアカウントにするのが単純）。Rules の関数（`myTags`・`isAdmin`・`canSee`）に、パスの `{t}` と Claims の `t` の一致を足す。`collectionGroup` のルールにも同じ条件が要る。テストは、式をまたぐ拒否のケースを全部の `match` に足す。

## 4. 管理者の権限の細分化

### いまの形と、困ること

- 権限は `admin: true` の 1 種類。意味は「新郎新婦」で、**全ゲストの本名・出欠・アレルギー・顔の記録・運営のメモ・すべての投稿（新郎新婦あての私信を含む）**を読め、ゲストの承認・タグ・投稿の非表示・AI の試験ができる。
- BP 会社の担当者に同じ権限を渡すと、仕事に要らないもの（私信、顔の記録、AI の試験）まで見える。「閲覧だけ」の人も作れない。
- 付け外しは、運営者の手元のコマンドだけ（CLAUDE.md ルール 7）。担当者の入れ替わりのたびに、運営者の作業が要る。

### 役割の案

| 役割 | 誰 | できること（案） | できないこと |
|---|---|---|---|
| 運営者 | サービスの運営者 | インフラ・鍵・役割の付け外し。**アプリの中の役割ではない**（クラウドのアカウントの権限） | — |
| `admin`（いまのまま） | 新郎新婦 | すべて（いまと同じ） | 役割の付け外し |
| `staff`（担当者） | BP 会社の担当者 | ゲストの一覧と承認、タグ、出欠・アレルギーの閲覧と書き出し、名簿の取り込み、投稿の非表示、合言葉のロックの解除 | 新郎新婦あての投稿の閲覧、顔の記録、AI の試験・音声、運営のメモ、エピソードの本文（要るかはヒアリングで聞く） |
| `viewer`（閲覧だけ） | 会場のスタッフ、BP 会社の上長など | ゲストの一覧と、出欠・アレルギーの閲覧 | 変更の操作すべて |

- 線を引く場所は、ヒアリングで決める（[commercial-readiness.md](../sales/commercial-readiness.md) §3 の「担当者の権限の分け方」）。上は、扱いに気をつける情報（顔・私信・運営のメモ）を、担当者から外した案。
- **アレルギーを誰が見るか**は、目的（料理の手配）から決める。会場のスタッフに `viewer` を渡すなら、見せる項目をさらに絞る案もある。

### 移行の案（`admin` の 1 種類から）

`admin` の意味は変えない。**足すだけ**にして、いまの式の動きを変えない。

1. **Claims に `role` を足す**（`"staff"` か `"viewer"`。無ければ、いまと同じ）。`admin: true` はそのまま全権。`applyGuestTags()` は既存の Claims とマージするので、`role` は消えない。付け外しは、`make-admin.mjs` と同じ形の手元のコマンドから始める（ルール 7 の考え方を保つ）。
2. **Rules:** `isStaff()`・`isViewer()` を足し、読み取りの条件を `match` ごとに開ける（`guestPrivate` の get / list など）。**書き込みは、いまも API（Admin SDK）だけなので、Rules の書き込みは変えない。**`posts` の `canRead` は変えない（担当者に私信を見せない）。
3. **API:** `withGuard` の `auth: "admin"` を、役割の一覧を受け取れる形に広げる（例: `roles: ["admin", "staff"]`）。ルートごとに、どの役割を通すかを決める。ハンドラの中の `admin === true` の確認も、同じ判定に揃える。
4. **監査ログ:** `actorRole` に `staff`・`viewer` を足す。拒否の記録（`admin.denied`）は、いまの仕組みのまま使える。
5. **画面:** 管理画面の項目を、役割で出し分ける。出し分けは見た目だけで、守りは 2 と 3。
6. **テスト:** Rules のテストに、役割ごとの許可と拒否のケースを足す（`harness.mjs` の人物に、担当者と閲覧者を足す）。

- **最初の一歩は `viewer`。**読み取りだけなので、Rules の変更が小さく、事故が起きにくい。次に `staff`。
- 役割を、担当者どうしで付け外しできる画面は、作らない（当面）。権限の昇格の経路を、アプリの中に持たない。
- **提供の形が「運営者が運用まで行う」なら、この節は不要。**担当者が管理画面を使うと決まってから作る。

## 5. 管理画面での監査ログの閲覧

**いまの形:** 更新系の API の記録が Firestore の `auditLogs` に 400 日、その写しが GCS（ロック済み）に 400 日。Rules は、だれにも読ませない。見る手段は、運営者のコマンド（`ops.mjs audit`）だけ。中身は、だれが（uid）・いつ・どの操作を・どの項目を。値は入らない。

**要るか:** 法人のチェックシートでは「利用者が操作の記録を確認できるか」が聞かれる（[security-answers.md](../sales/security-answers.md) §5 では「未実施」）。運営者が 1 名であることを補う手段にもなる（提供先が、運営者や担当者の操作を自分で見られる。[certification-roadmap.md](../sales/certification-roadmap.md) §4）。ただし、要るかどうかは相手による。

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| a. 依頼に応じて書き出す | 運営者が、期間と式を決めて、コマンドの出力を渡す。手順を文書にする | 実装が要らない | 運営者の操作を、運営者が出す形になる。相手は好きなときに見られない |
| b. 管理画面に、読み取り専用の一覧 | 管理者向けの API（ページ送り・期間と操作の絞り込み）と画面。Rules は閉じたまま、API だけが読む | 相手が自分で見られる | 画面に出す前に、uid（LINE のユーザー ID を含む）をニックネームに置き換える処理が要る。**一覧を見たこと自体も、記録に残す**（いまの監査は更新系だけ）。運営者がコマンドで行った操作（`make-admin` など）は、`auditLogs` に入らないものがある |
| c. ログを、相手の保管場所に送る | GCS の写しや Cloud Logging を、相手のバケット・SIEM に転送する | 相手の側で保全できる | 相手ごとの作り込み。A の方式なら、式ごとの設定になる |

**提案:** いまは a（手順を文書にするだけ）。担当者の役割（§4）を作るときに、b を一緒に作る。c は、求められたら考える。

- 分離の方式 A なら、ログは式ごとに分かれているので、b は「その環境のログを全部出す」だけで済む。B なら、ログにも式の ID を足し、絞り込みの漏れが、ほかの会社への漏えいになる。
- 個人情報の閲覧の記録（GCP の Data Access ログ）は、別の仕組みで、画面には出さない（LINE の表示名が入っている。[data-inventory.md](../privacy/data-inventory.md) §4）。

## 6. 認証の方式（SSO は要るか）

**前提（提案）:** ゲストは LINE のまま。LINE を使わないゲストへの対応は、ヒアリングで件数を聞いてから考える（代理での回答の登録など、ログインを足さない方法もある）。

担当者のログインは、提供の形で分かれる。

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| 1. 担当者も LINE | いまのまま。担当者の LINE のアカウントに、役割を付ける | 実装が要らない | 個人の LINE を業務に使うことになる。退職しても、会社の側ではアカウントを止められない（運営者に役割を外してもらう必要）。法人の基準で通らないことがある |
| 2. Google / Microsoft のアカウント | Firebase Authentication の、Google か Microsoft のログインを足す。会社のアカウントでログインし、退職時は会社がアカウントを止めれば入れなくなる。多要素認証も、会社の設定に従う | 会社が、入れる人を自分で管理できる。SAML ほどの手間が無い | ログインの入口が 2 つになる（`/api/auth/line` のほかに、担当者用）。**だれでもログインはできてしまうので、役割の無いアカウントには何も見せない**ことを Rules と API で確かめる。uid が `line:` で始まる前提の処理（Sentry の伏せ字、削除の手順）を見直す。CSP と、Firebase の API キーのリファラー制限に、ログイン用のホストを足す |
| 3. SAML / OIDC の SSO | 会社の ID 基盤と直接つなぐ。Firebase Authentication を Identity Platform に上げる必要がある（**料金と条件は要確認**） | 大きな会社の基準に合う | 会社ごとの設定と、つなぎ込みの支援が要る。式ごとの環境（A）では、環境ごとに設定が要る |
| 4. メールのリンク | メールアドレスに届くリンクでログイン | 簡単 | メールの乗っ取りに弱い。多要素にならない |

**提案:** **SAML の SSO は作らない（見送り）。**担当者が管理画面を使うと決まり、LINE では通らないと分かったら、2 を足す。入れる人は、メールアドレス（またはドメイン）の許可リストと、手元のコマンドで付ける役割の、両方で絞る。

- 「SSO が必須か」「担当者のログインに、会社のアカウントを使いたいか」は、ヒアリングの項目に入れてある。
- 運用に使うアカウント（Vercel・GCP など）の SSO は、別の話（Vercel の SAML は、有料の追加機能。[commercial-readiness.md](../sales/commercial-readiness.md) §1）。

## 7. 可用性・DR

### 稼働率の実力値

**測っていない。**外からの死活監視が無いので、過去の停止の時間も分からない（[alerting.md](../ops/alerting.md) §5）。約束できる数字は無い。

利用しているサービスの保証（**どれも要確認。プランによって、保証が無いものがある**）:

| サービス | 役割 | 公式の保証（確かめた範囲） |
|---|---|---|
| Vercel | 画面と API | Hobby・Pro での稼働率の保証は、確かめられていない（Enterprise の契約事項の可能性） |
| Firestore（東京・1 リージョン） | データベース | Google の SLA のページを読み取れなかった（リージョン 1 つの構成の数字を、公式のページで確かめる） |
| Firebase Authentication | ログイン | 未確認 |
| Cloudflare R2 | 写真 | SLA のページに「月間 99.9%」とある。どのプランに適用されるかは未確認 |
| LINE ログイン | ゲストのログイン | 未確認 |

ログインには、LINE・Vercel・Firebase Authentication のすべてが要る。**全体の稼働率は、いちばん弱いものより低くなる。**各社の保証をそのまま足し合わせて「99.x%」と言うことはできない。

### 単一障害点

| 何が止まると | 影響 | いまの備え |
|---|---|---|
| **運営者（1 名）** | 障害に気づく人・直す人がいない。鍵の入れ替え・復旧・連絡が止まる | 無い。引き継ぎ先は決まっていない（[certification-roadmap.md](../sales/certification-roadmap.md) §4 の案 5） |
| Vercel | 画面も API も出ない。開いたままの画面は、Firestore を直接読む・書く操作だけ続く（文字の投稿・コメント・いいね） | 無い（別の配信先は無い）。デプロイの巻き戻しはできる |
| Firestore（東京） | ほぼ全部。監査ログが書けないので、更新系の API も止まる（fail-closed） | PITR・日次・週次のバックアップ。別のリージョンへの切り替えは無い |
| LINE ログイン | 新しくログインできない。ログイン済みの人は、続けて使える | 無い（ほかのログインの方法は無い） |
| R2 | 写真が出ない・上げられない。文字の投稿は動く | **バックアップが無い**（[backup-restore.md](../ops/backup-restore.md) §4） |
| Worker | 高画質版の公開が遅れる。軽量版は見える | 止まったことに気づく仕組みが無い |
| Rekognition・Vertex AI・Modal | 顔の検出・AI・音声が止まる。本筋は動く | — |
| Sentry | エラーの通知が来ない。アプリは動く | — |
| Cloudflare の DNS・ドメインの登録 | 全部 | アカウントの保護（多要素認証） |
| Terraform の state（ローカル） | インフラの変更ができなくなる（動いているものは止まらない） | 無い（[backup-restore.md](../ops/backup-restore.md) §6） |

### 復旧の目標

いまある目安は [backup-restore.md](../ops/backup-restore.md) §2（7 日以内の事故なら、RPO は分単位。複製に約 12 分。書き戻しは未計測）。**約束できる RTO は無い。**

**提案: 「披露宴の当日の時間帯」と「それ以外」で、目標を分ける。**このサービスの価値は当日に集中する。

| | 当日の時間帯 | それ以外 |
|---|---|---|
| 体制 | 運営者が待機する（現地か遠隔かは、契約で決める） | 営業日の対応 |
| 目標（約束ではなく、努力目標として示す） | 気づいてから動き出すまで: すぐ。巻き戻し・メンテナンス表示までの時間を、訓練で測って示す | 受付から返信までの時間を示す |
| 備え | 当日の朝の確認（[incident-response.md](../ops/incident-response.md) §7）、前日からのデプロイの凍結、会場で回線が切れたときの投影の代わり | — |

### 上げる順番（効果の大きい順）

1. **外からの死活監視と、通知**（いまは、落ちても気づけない）。稼働率の実績も、ここから測り始められる。
2. **引き継ぎ先**（運営者が動けないときに、止める・連絡する人）。
3. **写真のバックアップ**と、**Terraform の state のリモート化**（どちらも、方針が未決定）。
4. **検証用の環境**と、**当日前のデプロイの凍結の決まり**（式ごとの環境にすると、1 回のマージが全部の式に出る）。
5. 訓練（机上と、メンテナンスの切り替え）で、動き出すまでの時間を測る。
6. 見送り: 複数リージョン化、Vercel 以外への配信の二重化、LINE 以外のゲストのログイン。費用と複雑さに、いまの規模が見合わない。

## 8. 課金・契約の単位と、データ構造

アプリの中に、課金の仕組み（決済・請求）は作らない前提。影響するのは「何を数える必要があるか」と「何を、どの単位で止める・消すか」。

| 単位 | 数えるもの | データ構造への影響 | 分離の方式との相性 |
|---|---|---|---|
| **式ごと** | 式の数、開催日 | 式の台帳（式・会社・開催日・状態・保持の期限）。アプリのデータは変えない | **A と合う。**環境 = 式 = 請求の単位。クラウドの利用料も、式ごとに見える |
| 年額（会社ごと） | 契約の期間、その間の式 | 会社 → 式の関係を持つ台帳。期間が切れたときに、式の環境をどうするか（読み取りだけにする、消す）の決まり | A でも B でもよい。会社をまたぐ一覧は、台帳で持つ |
| ゲストの数 | 式ごとの承認済みのゲストの数 | 数は、いまのデータから数えられる（`guests` の承認済みの件数）。上限を超えたときに止めるなら、承認の API に確認を足す | どちらでもよい |
| 利用量（写真の枚数・容量） | R2 の使用量、顔の検出の回数 | 式ごとに数える仕組み。A なら、バケットとプロジェクトの利用量がそのまま使える | A と合う |

**提案:** **式ごと**を基本にする。台帳は、最初は非公開の表（式・会社・環境の場所・開催日・保持の期限・片づけの予定日・担当者の役割の付与の記録）で持つ。式が十数件を超えたら、台帳を運用用の小さなデータベースにする。

- 台帳には、会社名と式の日付が入る。**公開のリポジトリには置かない。**
- 保持の期限（式のあと、いつ消すか）は、契約で決まる（[deletion-runbook.md](../privacy/deletion-runbook.md) §4 の案 A〜C）。式ごとの環境なら、期限ごとに環境を片づければよい。
- 当日だけ増える費用（音声合成の GPU を常時起動にする、など）を、料金に含めるかを決める。

## 9. 区分（必須／推奨／見送り）

「必須」は、**最初の 1 件の法人の式を受ける前**に要るもの。提供の形で変わるものは、条件を書いた。

| 区分 | 項目 | 条件・理由 |
|---|---|---|
| **必須** | 分離の方式を決める（提案は A） | これが決まらないと、ほかの設計が決まらない |
| 必須 | 式ごとの設定を、ソースと環境変数の外に出す（招待状の中身・投影のタグ。合言葉は式ごとの環境変数でよい） | A でも B でも要る。いまは、式を変えるのにコードの変更が要る |
| 必須 | 環境を作る・点検する・片づける手順の自動化（Terraform の state を式ごとに・リモートに。作成のチェックリスト。設定の点検のスクリプト） | A の弱点（運用の負荷と、設定の付け忘れ）への対策 |
| 必須 | 外からの死活監視・通知のルール・GCP のアラートの適用 | いまは、落ちても気づけない（Issue #104 の残り） |
| 必須 | 式の終了の手順（保持の期限、写真の引き渡し、環境の片づけ、消去の報告） | 契約で聞かれる。いまの手順は「すべてを消す」の順番だけ |
| 必須 | 商用のプランへの変更と、検証用の環境 | [commercial-readiness.md](../sales/commercial-readiness.md) §1 |
| 必須（担当者が管理画面を使う場合） | 役割の細分化（`viewer` → `staff`） | 担当者に `admin`（全権・私信の閲覧を含む）を渡さないため |
| **推奨** | 監査ログの、管理画面での閲覧（読み取り専用） | チェックシートで聞かれる。役割の細分化のあと |
| 推奨 | 担当者の、Google / Microsoft のアカウントでのログイン | LINE では通らないと分かったら |
| 推奨 | 式の台帳 | 最初は表でよい |
| 推奨 | 写真のバックアップ、引き継ぎ先 | 方針が未決定（Issue #104・[certification-roadmap.md](../sales/certification-roadmap.md) §4） |
| 推奨 | 顔の検出を、式ごとに切れるようにする | 要らない相手には外せる。扱う情報が減る |
| 推奨 | CTF の名残を、法人向けの環境から外す | 使わない入口を残さない |
| **見送り** | 同じプロジェクトの中でのマルチテナント（B・C） | 事故の広がり方と、作り直しの量。同時に動く式が十数件を超える見込みが立ってから |
| 見送り | SAML / OIDC の SSO | 求められてから |
| 見送り | 複数リージョン化・配信の二重化 | 費用と複雑さが、規模に見合わない |
| 見送り | アプリの中の課金・自分で申し込める形（セルフサービス） | 式ごとに運営者が環境を用意する形で始める |
| 見送り | 担当者どうしで役割を付け外しする画面 | 権限の昇格の経路を、アプリの中に持たない |
| 見送り | ログの、相手の保管場所への転送 | 求められてから |
